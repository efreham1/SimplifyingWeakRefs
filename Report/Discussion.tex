\chapter{Discussion}
\label{chap:discussion}

Across both benchmarks, the pipeline optimisations improve the metrics they directly target while leaving broader collection behaviour largely unchanged. The \texttt{weak\_fields} variant stands apart: by eliminating \texttt{WeakReference} objects from the heap entirely, it propagates improvements through every phase of the collection cycle rather than just the reference processing phase. The following sections explain the mechanisms behind these patterns and reflect on the scope of the evaluation.

\section{Superadditive Interaction of the Clear Path and Dynamic Array}
\label{sec:discuss-synergy}

The most striking result is that combining the clear-path optimisation with the dynamic array produces an 81\% reduction in non-strong processing time, far larger than the sum of their individual contributions (7\% and 36\% respectively). This superadditivity arises from the tight coupling of the two mechanisms at the implementation level.

In \texttt{dyn\_only}, the dynamic array provides improved cache locality during traversal: discovered references are stored contiguously in memory, so iterating through them involves sequential cache-line loads rather than following pointer chains scattered across the heap~\cite{drepper07-memory}. However, the per-reference processing logic still uses the standard CAS-based clear path, including a load barrier on the referent field and a CAS operation to atomically set the cleared referent to a coloured null pointer. These operations are not eliminated by the array alone.

In \texttt{clear\_path\_only}, the specialised clear logic eliminates the CAS on the referent field for old-generation referents (replacing it with a direct store) and removes the virtual call to determine the reference type. However, the referent field address and value must still be loaded individually for each reference during processing, and traversal still follows the intrusive linked list with its associated cache misses.

When both optimisations are active in \texttt{clear\_path\_dyn}, the dynamic array enables a further key capability: the referent field address and value are pre-fetched during discovery and stored directly in the array entry (see \cref{lst:dynamic-array-processing}). Processing then reads these values from the contiguous array without issuing any additional heap loads. The specialised clear path operates on the pre-fetched data, removing both the load-barrier overhead and the pointer-chasing overhead simultaneously. Each optimisation removes a bottleneck that would persist if the other were applied alone.

\section{Why the Skip-Enqueue Separation Alone Provides Minimal Benefit}
\label{sec:discuss-sep-alone}

The skip-enqueue optimisation was motivated by the observation that the enqueueing stage performs unnecessary work for queue-less weak references: they are still linked into the pending list, transferred to the \texttt{ReferenceHandler} thread, and iterated over only to be discarded~\cite{openjdk-reference-java,openjdk-zreferenceprocessor-cpp,JDK-8029205}. Despite this, \texttt{sep\_only} reduces the single-object median by only 5\% and shows no reduction at all in the multi-object benchmark.

The enqueue stage is not the bottleneck. The dominant costs in the baseline pipeline occur in the processing stage: each reference requires a load barrier on the referent field, a virtual call to determine the reference type, and a CAS operation to clear the referent. These operations are executed in the concurrent GC phase for every discovered reference. The enqueue stage, by contrast, involves linking references together via their \texttt{discovered} field, prepending the list to the global pending list under a lock, and then a single thread iterating the pending list. For a workload with 20 million queue-less references, skipping the enqueue step saves comparatively little work relative to what the processing stage already costs.

Furthermore, \texttt{sep\_only} uses a separate linked list for queue-less references rather than a dynamic array, so per-reference traversal still suffers from the same cache-miss pattern as the baseline. The skip-enqueue separation routes these references away from the enqueue path, but does not reduce the cost of reaching that point.

\section{Dynamic Array as an Enabler of the Skip-Enqueue Benefit}
\label{sec:discuss-sep-dyn-amplification}

While \texttt{sep\_only} provides negligible benefit, \texttt{sep\_dyn} reduces non-strong processing time by approximately 42\% in the single-object benchmark, compared to \texttt{dyn\_only}'s 36\%. The additional reduction comes from two sources. First, \texttt{sep\_dyn} routes queue-less references to a dedicated dynamic array during discovery; the array traversal therefore operates over a known-homogeneous set where every entry belongs to the no-enqueue path. Second, the processing function for this separate array knows statically that no reference in its collection will be enqueued, allowing it to omit the per-reference queue check and the pending-list linking step, making the per-iteration work cheaper and improving instruction-cache behaviour in the hot loop.

This comparison illustrates that the skip-enqueue separation is not an independent optimisation: its value is contingent on the array providing cache-friendly traversal and a structurally simpler processing function. Without the array, skipping the enqueue step is a minor tail optimisation; with it, the entire hot loop for queue-less references is streamlined.

\section{The Concurrent-Mark Regression}
\label{sec:discuss-mark-regression}

In the single-object benchmark, variants with the dynamic array show slightly higher concurrent-mark times than \texttt{none}: \texttt{clear\_path\_dyn} at 2\,780\,ms and \texttt{all} at 2\,750\,ms, compared to \texttt{none}'s 2\,575\,ms. This is unexpected because the dynamic array is used exclusively during reference processing, not during marking, and should in principle have no effect on the mark phase.

One plausible explanation involves memory bandwidth pressure. With 20 million references discovered in a single cycle, the retained dynamic-array allocations amount to hundreds of megabytes of committed GC memory. The arrays are kept at peak capacity between cycles (see \cref{subsec:dynamic-array-impl}), so this memory remains resident throughout the subsequent concurrent mark phase. Concurrent marking must then trace the heap while these large buffers compete for cache lines and memory bandwidth with the marking data structures (live bitmaps, marking stacks, and remembered sets). Under memory pressure, the marking threads may experience increased cache-miss latency, stretching the concurrent mark phase.

A second possibility is that reference processing, which precedes marking in some generational ZGC cycle configurations, affects the subsequent marking phase through memory subsystem state such as cache eviction or TLB pressure. However, with IQRs of 560--810\,ms for this metric in the single-object benchmark and the pattern absent from the multi-object results, a causal attribution cannot be established with confidence. The regression could also be an artefact of sampling variability. A more targeted experiment -- running only the concurrent mark phase with and without large retained arrays -- would be needed to confirm the cause.

\section{Memory Overhead of the Pre-Fetched Array Entries}
\label{sec:discuss-mem-overhead}

The auxiliary GC memory results show a notable asymmetry among the dynamic-array variants: \texttt{dyn\_only} and \texttt{sep\_dyn} use 308\,MB in the single-object benchmark (157\% above \texttt{none}'s 120\,MB), while \texttt{clear\_path\_dyn} uses 1\,268\,MB (roughly 10$\times$ the non-array baseline) and \texttt{all} uses 884\,MB. This asymmetry directly reflects the per-entry struct size.

The \texttt{ZWeakRefArray} used in \texttt{dyn\_only} stores one entry per discovered reference containing the reference's address and its \texttt{discovered} field address, which is the minimum needed for processing. The \texttt{clear\_path\_dyn} variant uses an extended entry that additionally stores the referent field address and the pre-fetched referent field value, enabling the barrier-free clear path described in \cref{sec:optimised-clear-path}. With 20 million references in the single-object benchmark, this larger entry size directly multiplies the array footprint. The discrepancy between \texttt{clear\_path\_dyn} and \texttt{all} further reflects the fact that \texttt{all} routes queue-less references through the \texttt{sep} path's separate array, and the two arrays' capacities are maintained independently with slightly different reservation strategies.

In the multi-object benchmark, the same effect is visible but much smaller (24\% at worst for \texttt{clear\_path\_dyn}), because the two million references are spread across multiple collection cycles rather than all being discovered in a single cycle.

\section{Structural Advantage of Weak Fields}
\label{sec:discuss-weak-fields}

The \texttt{weak\_fields} variant achieves improvements across all measured GC metrics because its advantage is structural rather than algorithmic: eliminating the \texttt{WeakReference} wrapper objects reduces the number of live objects the GC must process in every phase of the collection cycle, not just in reference processing.

In the single-object benchmark, 20 million \texttt{WeakReference} objects are heap-allocated Java objects that must be allocated in the young generation, survive young collections, and be promoted to the old generation. Each such object carries a header, a referent field, a queue field, a next field, and a discovered field. The concurrent mark phase must trace all of them, contributing to the longer mark times observed for the \texttt{WeakReference} variants. Young-generation promotions add to young-generation collection time, explaining the 44\% reduction in the Young Generation (Promote All) metric: \texttt{WeakReference} variants promote 20 million wrapper objects in addition to the target objects, while \texttt{weak\_fields} promotes only the target objects.

The heap usage data confirms this directly: \texttt{weak\_fields} uses 806\,MB versus 1\,720\,MB for all \texttt{WeakReference} variants in the single-object benchmark (53\% lower). The 900\,MB difference corresponds almost exactly to 20 million \texttt{WeakReference} objects each occupying approximately 44--48 bytes (header plus four pointer fields on a 64-bit JVM with compressed references disabled), which is consistent with the ZGC heap layout for small Java objects.

In the multi-object benchmark the absolute effect is smaller because the 2 million references represent a smaller fraction of total heap activity: the 5\% heap reduction and 31\% old-generation reduction reflect a proportionally smaller eliminated object set relative to the benchmark's total GC workload. The tighter IQRs observed for \texttt{weak\_fields} across virtually all metrics are also consistent with this structural explanation: with fewer objects to trace, the GC cycle duration is less sensitive to variation in the reference processing workload, resulting in more consistent run-to-run timings.

\section{Processing Mechanics of Weak Fields}
\label{sec:discuss-wf-nonstrong-residual}

On the processing side, \texttt{weak\_fields} is mechanically similar to \texttt{sep\_dyn}. Entries discovered during old-generation marking are stored in a per-worker \texttt{ZWeakFieldArray}, the direct analogue of the \texttt{ZWeakRefArray} used by the dynamic-array \texttt{WeakReference} variants. Like queue-less \texttt{WeakReference} objects in \texttt{sep\_dyn}, weak-field entries carry no \texttt{ReferenceQueue} and therefore bypass the enqueue stage entirely: once the referent is found to be unreachable, the annotated field is zeroed without creating a pending-list entry.

This structural parallel is reflected in the non-strong processing times. \texttt{weak\_fields} achieves a 51\% reduction in the single-object benchmark, compared to \texttt{sep\_dyn}'s 42\% and \texttt{dyn\_only}'s 36\%. The somewhat better figure for \texttt{weak\_fields} is consistent with the simpler per-entry structure: annotated fields are stored and cleared directly, without the \texttt{WeakReference} object header, queue field, next field, and discovered field.

The result does not reach the 81\% reductions of \texttt{clear\_path\_dyn} and \texttt{all} for two reasons. First, the \texttt{ZWeakFieldArray} does not currently pre-fetch the referent value during discovery, so clearing the field still requires a load-barrier access, analogously to \texttt{dyn\_only} rather than \texttt{clear\_path\_dyn}. Second, JVM-internal \texttt{WeakReference} objects (used for class-loader metadata, interned strings, and internal caches) still go through the standard pipeline regardless of whether application code uses \texttt{@weak} fields, providing a floor below which the non-strong metric cannot fall.

\section{Limitations}
\label{sec:discuss-limitations}

Several aspects of the evaluation warrant care in interpreting the results.

\textbf{Benchmark representativeness.} Both benchmarks are custom microbenchmarks designed to isolate reference processing overhead. The single-object benchmark concentrates its entire weak-reference load into a single GC cycle, and the multi-object benchmark uses a fixed reference population with a regular promotion pattern. Neither benchmark captures the full diversity of real-world weak-reference usage, such as dynamic cache eviction, concurrent insertion and removal, or workloads with a mixture of queue-backed and queue-less references. The strong improvements observed on the non-strong processing metric may therefore represent an upper bound on what would be seen in a more heterogeneous production workload.

\textbf{Single hardware platform.} All measurements were collected on a single UPPMAX cluster configuration (see \cref{sec:cluster-setup}). The results may not generalise to different CPU micro-architectures, NUMA configurations, or cache hierarchy sizes. In particular, the memory bandwidth pressure hypothesis for the concurrent-mark regression is architecture-dependent.

\textbf{Correctness coverage.} The correctness of the implementation was verified through the standard OpenJDK test suite and manual inspection, not through formal verification or an exhaustive stress suite for the weak-field annotation. In particular, the compiler and interpreter support for \texttt{@weak} annotated fields is complex and spans three execution tiers; corner cases in tier-to-tier deoptimisation paths may not have been exercised.

\textbf{Unconfirmed causal attributions.} The concurrent-mark regression in single-object dynamic-array variants has a plausible explanation in memory-bandwidth pressure (see \cref{sec:discuss-mark-regression}), but confirming it would require additional instrumentation or targeted experiments to distinguish the proposed mechanism from other confounders.

\textbf{Weak-field generality.} The \texttt{weak\_fields} implementation does not support young-generation objects or queue-based callbacks, meaning it cannot serve as a drop-in replacement for all uses of \texttt{WeakReference}. The evaluation therefore compares it only against the subset of \texttt{WeakReference} usage that does not require queue callbacks, which corresponds to the same use case targeted by the \texttt{WeakReference} pipeline optimisations.

\section{Future Work}
\label{sec:discuss-future-work}

Several directions emerge naturally from this work.

\textbf{Production workload evaluation.} The most immediate extension would be to evaluate the optimised variants on real-world applications with diverse weak-reference usage patterns, such as application servers or build tools that use \texttt{WeakHashMap} extensively. A production trace would reveal whether the 81\% non-strong processing improvement translates into meaningful end-to-end latency improvements in a multi-threaded workload where reference processing competes with other GC work.

\textbf{Investigating the concurrent-mark regression.} The elevated concurrent-mark times in dynamic-array variants in the single-object benchmark should be investigated with targeted profiling. Instrumenting ZGC to report cache-miss rates and memory bandwidth consumption during the concurrent mark phase, with and without large retained arrays, would either confirm or refute the memory-bandwidth-pressure hypothesis proposed in \cref{sec:discuss-mark-regression}. If confirmed, mitigations such as releasing array capacity at the end of a cycle rather than retaining it would be worth exploring.

\textbf{Extending the clear-path optimisation.} The specialised clear path is currently limited to old-generation \texttt{WeakReference} objects without a \texttt{ReferenceQueue}. Extending it to cover \texttt{SoftReference} and \texttt{PhantomReference} objects in the queue-less case, or to handle cross-generational references more efficiently, could yield additional reductions in non-strong processing time. The safety argument for omitting the CAS depends on the constrained update model described in \cref{sec:optimised-clear-path}, and it would need to be re-examined for each additional reference type.

\textbf{Weak-field support for young-generation objects and callbacks.} The current weak-field implementation skips young-generation fields and provides no queue-based notification mechanism. Adding young-generation support would require careful integration with the young-generation marking and remembered-set machinery, as weak-field discovery currently runs only during old-generation marking. Adding optional callback support would make \texttt{@weak} a closer replacement for the full \texttt{WeakReference} API and would allow a broader comparison across more use cases.

\textbf{Upstream integration.} The skip-enqueue separation, the dynamic array, and the clear-path optimisation are all independent changes with well-defined correctness arguments. Submitting one or more of them to the OpenJDK project for review would allow the broader community to evaluate the trade-offs and potentially integrate the improvements that pass the upstream quality bar. The JDK-8029205 enhancement request provides a natural entry point for such a submission.

\textbf{Array capacity management strategies.} The current strategy of retaining array capacity between GC cycles (keeping enough capacity for the previous cycle's count) is simple but may over-allocate on bursty workloads. Alternative strategies, such as exponential decay of reserved capacity or cycle-to-cycle capacity smoothing, could reduce the steady-state auxiliary memory footprint without significantly increasing reallocation frequency.
