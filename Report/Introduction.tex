\chapter{Introduction}
\label{chap:introduction}

    Java is one of the most widely used programming languages in enterprise and server-side computing~\cite{wiki-lang-popular-websites}, where applications routinely manage heaps ranging from tens to hundreds of gigabytes. In such environments, the performance of the Java Virtual Machine's (JVM) garbage collector (GC) directly affects application latency and throughput. The Z Garbage Collector (ZGC) addresses this challenge by performing nearly all garbage collection work concurrently with the application, thereby achieving millisecond-scale pause times regardless of heap size~\cite{jep333-zgc}.

    However, one aspect of ZGC that has received comparatively little optimisation attention is the processing of \emph{weak references}. In Java, the class \texttt{WeakReference} provides weak semantics, allowing applications to retain references to objects without preventing those objects from being collected~\cite{oracle-ref-javadoc,openjdk-weakreference-java}. When the garbage collector determines that an object is only reachable through a \texttt{WeakReference}, i.e. no longer strongly reachable, it clears the reference and, if the reference is associated with a \texttt{ReferenceQueue}, enqueues it for application-level processing~\cite{openjdk-reference-java,openjdk-referencequeue-java}. This enqueueing step serves as a garbage collector callback, notifying the application that the \texttt{WeakReference} has been cleared. Weak semantics, both with and without such callbacks, are used in a range of programming patterns and data structures, for example the Java library \texttt{WeakHashMap}~\cite{openjdk-weakhashmap-java}.

    The current ZGC reference-processing pipeline treats all weak references uniformly: discovered references are linked into an intrusive linked list, processed, and then handed to a Java-level daemon thread (the \texttt{ReferenceHandler}) for enqueueing~\cite{openjdk-zreferenceprocessor-cpp,openjdk-reference-java}. This design imposes disproportionate overhead on weak references that are not registered with a \texttt{ReferenceQueue}. Such references are used solely for weak semantics and therefore do not require the callback mechanism provided by the queue. Nevertheless, the full \texttt{WeakReference} object must still be allocated and processed, even though the application has no need for enqueueing.

    This inefficiency has previously been identified in the OpenJDK bug tracker~\cite{JDK-8029205}, which notes the unnecessary traversal of the pending list for references without a \texttt{ReferenceQueue}. However, as of April 2026, no implementation addressing this issue has been integrated into the JDK. Building on that observation, this thesis investigates whether targeted modifications to ZGC's reference-processing pipeline can reduce this overhead. It explores three orthogonal optimisation approaches for \texttt{WeakReference}-based processing: skipping the enqueue path for references without queues, replacing the intrusive linked list with a cache-friendly dynamic array, and reducing per-reference instruction cost through an optimised clear path. In addition, it examines a weak-field mechanism as an alternative implementation of weak semantics that avoids the overhead of \texttt{WeakReference} objects entirely.

    \section{Motivation}
    \label{sec:motivation}

        Weak references are handled very specifically in JVM garbage collection. Unlike regular references, which are handled implicitly by the mark phase, weak references require explicit processing by the collector~\cite{openjdk-zreferenceprocessor-cpp,openjdk-referenceprocessor-cpp}. Each discovered weak reference must be individually evaluated, its referent field cleared if the referent is unreachable, and the reference potentially enqueued. This per-reference processing cost scales linearly with the number of weak references, making it a bottleneck in applications that allocate millions of them.

        The problem is amplified by a mismatch between the API design and its implementation. Java's \texttt{WeakReference} API provides an optional \texttt{ReferenceQueue} parameter~\cite{openjdk-weakreference-java}, allowing applications to choose whether they want the callback mechanism. However, ZGC's reference processor does not take advantage of this distinction, treating all weak references as if they require enqueueing. This results in unnecessary work for references that do not use a \texttt{ReferenceQueue}, which is a common case in practice. At the same time, weak semantics are currently realised through separate \texttt{WeakReference} objects, so applications also pay the allocation and processing cost of those objects even when they only need conditional reachability.

        ZGC's concurrent architecture makes both of these inefficiencies particularly relevant. Because ZGC processes references concurrently with the application~\cite{jep333-zgc,openjdk-zreferenceprocessor-cpp}, any reduction in per-reference overhead translates directly into less time spent in the reference processing phase. This motivates two complementary lines of investigation: optimising the existing \texttt{WeakReference} pipeline for the common queue-less case, and exploring whether weak semantics expressed through annotated object fields can reduce overhead further by avoiding \texttt{WeakReference} objects altogether.

    \section{Problem Statement}
    \label{sec:problem-statement}

        The current ZGC reference processing pipeline does not distinguish between weak references with and without a \texttt{ReferenceQueue} during its phases~\cite{openjdk-zreferenceprocessor-cpp}. All cleared references are threaded onto a pending list, transferred to the \texttt{ReferenceHandler} thread, and iterated regardless of whether they will actually be enqueued~\cite{openjdk-reference-java}. Additionally, the intrusive linked-list data structure used for discovered references exhibits poor cache locality~\cite{chilimbi99}. Beyond these pipeline inefficiencies, representing weak semantics through separate \texttt{WeakReference} objects introduces object and heap overhead that may be avoidable if weak reachability is instead expressed directly through annotated object fields.

    \section{Research Questions}
    \label{sec:research-questions}
        The research questions that this thesis aims to address are:
        \begin{itemize}
            \item[\textbf{RQ1}] \label{rq:weakref-opt} How do modifications to ZGC's processing of \texttt{WeakReference} objects without a \texttt{ReferenceQueue} affect the wall-clock time of reference processing, the total GC cycle time, the GC memory footprint, and Java heap usage in select workloads?
            \item[\textbf{RQ2}] \label{rq:weak-fields} How does expressing weak reachability through annotated object fields affect reference processing time, GC cycle time, GC memory footprint, and Java heap usage compared to the optimised \texttt{WeakReference}-based approach of RQ1?
        \end{itemize}


    \section{Scope and Delimitations}
    \label{sec:scope}
        This thesis focuses on the reference processing pipeline within ZGC, specifically targeting weak references without a \texttt{ReferenceQueue}. The primary implementation work concerns \texttt{WeakReference}-based processing, with weak fields treated as an extension evaluated in the same benchmarking framework. Although the optimisation approaches are described in general terms the implementation and evaluation remain ZGC-specific. Furthermore, some of the optimisations, such as the optimised clear path, may have broader applicability beyond just weak references without a \texttt{ReferenceQueue}. However, these broader applications fall outside the scope of this thesis and are not evaluated.

        The correctness of the optimisations is verified through the standard OpenJDK test suite and manual inspection; formal verification is outside the scope of this work. Performance measurements are conducted on a single hardware platform under controlled conditions and therefore may not generalise to all environments.
